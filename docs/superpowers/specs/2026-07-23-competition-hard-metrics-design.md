# 赛项硬指标补齐设计规格

**日期：** 2026-07-23  
**状态：** 已确认，待实施计划  
**范围：** 岗位层级、数据质量门禁、季度动态演化、赛项验收统计

## 1. 背景与目标

当前系统已经具备JD导入、岗位画像、知识图谱、知识问答、人岗匹配和自动评测能力，但现有数据仍存在单批次、层级统一为`all`、异常日期较多、季度演化证据不足和验收指标缺少统一出口等问题。

本次改造建立一条可重复运行、可追溯、不可手工伪造达标状态的硬指标流水线，并对现有1852条入库JD执行一次非破坏式全量重算。后续新增数据沿用相同规则增量更新。

### 1.1 成功标准

- 每条JD都有确定的质量门禁状态，异常原因可查询。
- 通过门禁的JD具备`junior`、`mid`、`senior`、`expert`或`unspecified`层级及判定证据。
- 岗位画像按岗位、技术栈、层级和自然季度生成。
- 相邻季度能够生成新增、删除、修改三类能力变化，且每条变化可追溯到原始JD。
- 系统自动计算赛项最低要求和国奖内部目标，不允许手工填写达标结果。
- 流水线重复运行不会产生重复画像、重复演化事件或重复验收记录。
- 原始JD、外部标准证据、知识库、简历、匹配和评测记录均不丢失。

### 1.2 非目标

- 本阶段不扩充到5000至10000条数据，只准确展示当前缺口。
- 本阶段不制作PPT、视频和正式答辩材料。
- 本阶段不重写简历解析和匹配算法。
- 本阶段不修改知识问答的主要交互流程。

## 2. 总体架构

新增独立的硬指标流水线，复用现有导入、技能抽取、画像和图谱能力，不继续扩大现有分析服务的职责。

```text
原始JD
  -> 日期、来源和完整性校验
  -> 重复及低质量数据门禁
  -> 岗位层级识别
  -> 按岗位、技术栈、层级和季度分组
  -> 生成季度岗位画像
  -> 对比相邻季度
  -> 生成新增、删除、修改事件及证据关联
  -> 同步知识图谱
  -> 生成赛项验收快照
```

流水线包含五个边界清晰的组件：

1. `QualityGateService`：计算质量状态和问题代码，不删除原始数据。
2. `SeniorityClassifier`：计算岗位层级、置信度和判定依据。
3. `QuarterlyProfileService`：聚合通过门禁的JD并生成季度画像。
4. `EvolutionService`：比较相邻季度，生成能力变化和证据关联。
5. `AcceptanceService`：从数据库和真实评测记录计算验收状态。

## 3. 数据质量门禁

### 3.1 状态定义

- `valid`：通过全部硬校验，可参与季度画像和演化计算。
- `review`：数据可保留，但存在日期、来源、文本质量或层级冲突，需要人工复核；不参与画像。
- `quarantined`：缺少关键字段或无法解析；不参与画像。
- `duplicate`：完全重复或高相似重复；只保留主记录参与画像。

状态优先级为`quarantined > duplicate > review > valid`。一条JD可以有多个问题代码，但只能有一个门禁状态。

### 3.2 硬校验规则

以下情况标记为`quarantined`：

- 缺少记录编号、岗位名称、岗位描述、岗位族、来源名称或采集时间。
- 岗位描述去除空白和标点后少于40个字符。
- 发布时间或采集时间存在但无法解析。

以下情况标记为`review`：

- 发布时间晚于采集时间1天以上。
- 发布时间晚于流水线运行时间1天以上。
- 采集时间早于发布时间，或两者相差超过3653天。
- 来源链接存在但不是`http`或`https`地址。
- 无来源链接且来源类型不是职业标准、技术标准、政策文件或官方文件。
- 未识别到任何技能和职责。
- 综合质量分低于0.70。

以下情况标记为`duplicate`：

- 标准化正文哈希完全相同。
- 同一岗位族内SimHash汉明距离不大于8。重复组中来源分更高、发布时间更新、字段更完整的记录作为主记录；其余记录保存`duplicate_of_id`。

所有规则保存统一版本号。首个版本使用`competition-gate-v1`。

## 4. 岗位层级识别

### 4.1 层级集合

- `junior`：初级、助理、应届或实习岗位，或明确要求不超过2年经验。
- `mid`：明确要求3至5年经验，或职责强调独立交付但不包含技术领导职责。
- `senior`：高级、资深、架构师，明确要求6年以上经验，或包含架构设计、技术攻关、指导成员等职责。
- `expert`：专家、首席、技术负责人、技术总监，且包含技术规划、团队管理、跨部门决策或标准制定职责。
- `unspecified`：没有足够证据，或不同证据给出无法消解的冲突结论。

### 4.2 判定顺序和置信度

1. 岗位名称出现明确层级词时优先采用，置信度为0.95。
2. 没有明确层级词时解析经验要求：0至2年为`junior`，3至5年为`mid`，6年以上为`senior`，置信度为0.85。
3. 没有年限证据时使用职责特征，置信度为0.75。
4. `expert`必须同时满足专家类名称或职责证据中的一项，以及技术领导类职责证据中的一项；仅凭工作年限不能判为`expert`。
5. 名称、年限和职责结论冲突时，名称优先；冲突内容写入判定依据并将置信度降低0.10。
6. 最终置信度低于0.65时输出`unspecified`并进入人工复核列表。

判定结果保存层级、置信度、命中的规则、原始证据片段和规则版本，支持人工修改。人工修改必须保存修改人、修改时间和修改说明，不能覆盖机器判定原值。

## 5. 季度岗位画像

### 5.1 分组维度

使用发布时间所属自然季度，季度键格式为`YYYY-Q1`至`YYYY-Q4`。画像分组键为：

```text
岗位族 + 技术栈 + 岗位层级 + 季度
```

只有`valid`且非重复的JD参与画像。没有可靠发布时间的JD保留在数据库中，但不能进入季度画像。

### 5.2 样本门槛

- 每个画像切片至少需要10条有效且去重后的JD。
- 10至19条标记为`low_sample`，允许展示但不用于赛项就绪判定。
- 20条及以上标记为`ready`，可用于正式演化对比。
- 样本不足时不得合并非相邻季度或复制其他季度数据来制造变化。

### 5.3 画像内容

每个季度画像保存：

- 样本总量、有效样本量和来源数量。
- 核心职责及出现比例。
- 必备技能、加分技能、出现比例和证据数量。
- 典型行业场景。
- 层级、技术栈、季度和规则版本。
- 生成流水线运行编号与输入数据摘要哈希。

旧版无季度画像保留为`legacy`，不参与新的验收统计和演化计算。

## 6. 真实时间演化

### 6.1 比较范围

只比较同一岗位族、技术栈和层级的相邻自然季度。两个季度均达到`ready`后，变化才计入赛项就绪结果；低样本变化可以展示，但必须显示“样本不足”。

### 6.2 技能变化规则

设前季度出现比例为`before_rate`，当前季度出现比例为`after_rate`：

- `added`：`before_rate < 0.05`、`after_rate >= 0.15`、增幅不少于0.10，且当前季度至少有3条独立JD证据。
- `removed`：`before_rate >= 0.15`、`after_rate < 0.05`、降幅不少于0.10，且前季度至少有3条独立JD证据。
- `modified`：两个季度出现比例均不低于0.05，比例变化不少于0.10；或主要属性在“必备”和“加分”之间发生变化，且变化后的属性至少有3条独立JD证据。

职责变化采用标准化文本键进行新增和删除判定；首版不对语义相似但措辞不同的职责强行判为修改，避免产生不可解释结果。

### 6.3 证据要求

每条演化事件保存：

- 前后季度、前后比例、绝对变化幅度。
- 前后画像编号和流水线运行编号。
- 支持变化的原始JD编号、来源、发布日期和证据片段。
- 外部标准证据仅作为补充说明，不能替代真实招聘JD的时间变化证据。

没有足够证据时不生成正式事件，并在验收统计中显示缺口。

## 7. 数据存储与幂等性

### 7.1 JD扩展字段

- 机器层级、机器置信度、机器判定依据JSON。
- 人工层级、人工审核信息。
- 门禁状态、门禁问题代码JSON、门禁规则版本和门禁时间。

### 7.2 画像与演化扩展

继续使用现有`JobProfile`、`JobProfileSkill`、`JobProfileResponsibility`和`JobProfileScenario`，不建立平行画像表。`JobProfile`增加以下字段：

- `profile_kind`：`legacy`或`quarterly`。
- `period_key`：季度画像使用`YYYY-QN`，旧画像为空。
- `sample_count`和`sample_status`：记录有效样本量及`insufficient`、`low_sample`或`ready`状态。
- `input_signature`：参与画像的JD编号和内容哈希生成的稳定摘要。
- `pipeline_run_id`：关联生成该画像的流水线运行。
- `generation_key`：规则版本、岗位族、技术栈、层级和季度组成的唯一生成键。
- `derivation_status`：`active`或`superseded`，与表示新岗位或既有岗位的原`status`字段分离。

现有`EvolutionEvent`增加前后季度、前后比例、变化幅度、事件状态、运行编号和唯一生成键。旧演化事件标记为`legacy`，不参与验收统计。

### 7.3 新增实体

- `PipelineRun`：运行编号、模式、规则版本、开始结束时间、输入量、各状态数量、错误摘要和运行状态。
- `EvolutionEvidence`：演化事件与原始JD之间的多对多证据关联。
- `AcceptanceSnapshot`：两个验收口径的指标值、达标状态、缺口和生成时间。

### 7.4 幂等规则

- 流水线使用“规则版本 + 输入摘要哈希 + 画像分组键”作为生成键。
- 相同生成键重复运行时更新同一派生结果，不新增重复记录。
- 输入或规则变化时生成新结果，并将旧结果标记为`superseded`，不物理删除。
- 每个岗位族和季度在独立事务中处理；单组失败不影响其他组，并记录失败原因。

## 8. 验收统计

### 8.1 赛项最低要求

- 独立JD解析评测样本不少于100条。
- JD解析、简历提取和人岗匹配三项Accuracy均不低于90%。
- 单元测试覆盖率不低于60%。
- 至少1个新岗位和1个既有岗位具备完整画像、来源证据和输入输出案例。
- 既有岗位存在至少一组相邻季度正式演化结果。

### 8.2 国奖内部目标

- 原始JD总量处于5000至10000条。
- 覆盖20至30类岗位和至少3类可追溯数据来源。
- 样板岗位覆盖至少3个层级和2个相邻的`ready`季度。
- 三项Accuracy目标为92%至95%。
- 有效率、重复率、待审核率、异常日期率和来源覆盖率均可解释并可追溯。

### 8.3 状态计算

每项输出`passed`、`failed`或`not_measured`，同时提供当前值、目标值和缺口数量。总状态只有全部最低要求为`passed`时才显示“赛项就绪”。任何指标没有真实记录时必须显示`not_measured`，不能按0分或默认达标处理。

## 9. 全量重算与安全措施

1. 重算前复制SQLite数据库并写入带时间戳的备份文件。
2. 执行向后兼容的数据结构迁移。
3. 对现有JD重新执行门禁和层级识别，不修改原始载荷。
4. 将旧版画像标记为`legacy`，创建新的季度画像。
5. 只基于相邻且样本达标的季度生成正式演化事件。
6. 同步知识图谱并生成验收快照。
7. 输出重算前后数据量、状态分布、岗位层级和季度覆盖对比。
8. 任一迁移步骤失败时停止后续步骤，保留原数据库和备份路径，不自动删除备份。

## 10. 接口与界面

新增或扩展接口用于：

- 启动全量重算或增量更新。
- 查询流水线运行进度和失败原因。
- 查询质量门禁及层级分布。
- 按岗位、技术栈、层级和季度查询画像。
- 查询相邻季度演化及原始JD证据。
- 查询赛项最低要求和国奖内部目标验收状态。

现有页面保持兼容。指标评测页面增加验收统计；能力演化页面增加季度和层级筛选；数据治理页面增加门禁状态、问题代码和流水线运行记录。页面不得把低样本演化显示为正式达标结果。

## 11. 测试策略

- 单元测试：日期、来源、文本长度、质量状态优先级和重复主记录选择。
- 单元测试：五类层级、证据冲突、低置信度和人工覆盖。
- 单元测试：季度边界、样本门槛及新增、删除、修改规则。
- 集成测试：全量重算、增量更新、重复运行幂等性和单组事务失败。
- 迁移测试：旧数据库字段扩展、旧画像保留和备份恢复可用性。
- 回归测试：知识图谱、知识问答、简历匹配和自动评测接口。
- 验收测试：缺失真实评测时必须显示`not_measured`，不能显示就绪。
- 完整测试覆盖率不得低于60%，内部继续以70%以上为目标。

## 12. 完成定义

- 全量测试通过且覆盖率不低于60%。
- 对数据库副本完成一次全量重算，再对正式数据库执行迁移。
- 两次连续运行产生一致的状态数量，且无重复派生记录。
- 重算前后对比报告可从系统查询。
- 验收统计准确反映当前数据缺口，不因缺少数据产生虚假达标。
- 用户可从演化事件追溯到季度画像和原始JD证据。
