# 可持续更新岗位知识库与知识图谱设计

## 1. 背景与目标

本设计面向 XH-202621“多源异构数据驱动岗位和能力图谱构建与动态演化分析研究”赛题，在现有 `langchain_deepseek` 岗位能力平台上构建可持续更新的岗位知识库与知识图谱。

系统以关系型数据库作为可审计的数据主库，以 Neo4j 作为比赛部署中的图查询与可视化存储，以全文/向量混合检索作为 RAG 知识库。三者共享稳定实体标识和原始证据，形成以下闭环：

```text
原始数据留存 -> 格式与质量治理 -> 岗位要素抽取 -> 岗位画像版本
             -> 知识库检索 -> 知识图谱发布 -> 后续数据增量更新
```

本阶段必须完成：

- 处理根目录现有 `jd_raw.json`，生成首批结构化知识库和知识图谱。
- 保留异常行和低质量记录，避免数据静默丢失。
- 使同一数据重复导入保持幂等，使修订数据能够保留历史。
- 对受影响岗位族执行局部重算，避免每次新增数据都全库重建。
- 使技能、职责、场景和演化结论可追溯到真实 JD 原文。
- 在 Neo4j 不可用时继续提供完整的数据治理、检索和图谱 JSON/API 能力。

## 2. 赛题要求映射

| 赛题要求 | 本设计对应能力 |
| --- | --- |
| 多源异构数据清洗与交叉验证 | 导入批次、原始行、质量规则、来源权重、重复识别、异常隔离 |
| 新岗位发现与定义 | 岗位族聚合、增长与新颖度评分、岗位画像版本、人工审核 |
| 既有岗位能力动态更新 | 内容签名、局部重算、版本链、能力新增/删除/修改事件 |
| 技能点级全景图谱 | 岗位、版本、技能、职责、行业场景、企业、地区、来源和证据节点 |
| 大模型、知识图谱、RAG | 证据约束抽取、Neo4j 图谱、全文/向量混合检索和带引用回答 |
| 幻觉防控 | 原文证据、置信度、低置信审核、无证据结果禁止正式发布 |
| 可验证性 | 真实数据构建报告、增量与幂等测试、证据追溯测试、覆盖率不低于 60% |

## 3. 当前数据基线

`jd_raw.json` 的文件扩展名为 `.json`，实际内容是每行一个 JSON 对象的 JSONL。实施前只读审计结果如下：

- 文件包含 1855 个非空数据行。
- 1854 行能够解析为 JSON 对象，1 行包含非法控制字符。
- 1854 个对象覆盖 8 个岗位族，全部来自同一采集者和智联招聘。
- 1854 个来源 URL 唯一，但岗位描述只有 1337 个唯一文本，存在明显内容重复。
- 现有字段模型可直接处理 1852 条；1 条描述过短，1 条企业名称超过长度限制。
- 现有技能词表能从可处理记录中识别 49 类技能，208 条记录未命中词表技能。
- 行业字段存在薪资、岗位要求等错位内容；发布日期包含 2000 至 2026 年数据及 8 个未知值。

这些数字用于校验首批流水线是否完整读取数据，不作为正式有效记录数量。正式数量由格式校验、质量规则和精确/近似去重共同决定。

## 4. 总体架构

采用“关系型主库 + Neo4j 图谱 + 混合检索知识库”的增强路线。

### 4.1 关系型主库

SQLite 为默认运行数据库，并保留通过 `DATABASE_URL` 切换 MySQL 的能力。关系型主库保存：

- 导入批次和原始数据行；
- 清洗后的 JD 及其修订历史；
- 规范化实体、关系、证据和质量问题；
- 岗位画像版本、演化事件和审核状态；
- 知识片段元数据和外部索引标识。

关系型主库是唯一事实来源。Neo4j 和检索索引均可由主库重建。

### 4.2 Neo4j 图谱

Neo4j 保存已生成的岗位画像图谱，服务于多跳查询、交互可视化和比赛演示。同步采用稳定业务标识执行 `MERGE`，不得用临时数据库自增编号作为跨存储唯一标识。

Neo4j 不可用时，导入和画像更新仍然成功，批次状态标记为 `graph_sync_pending`。恢复连接后可重新同步，不回滚主库数据。

### 4.3 混合检索知识库

首批部署对已持久化的 JD、职责、技能证据和外部证据执行确定性词法检索，保持零外部依赖和来源可追溯。Embedding 提供者配置完成后，额外保存片段向量，并按以下方式融合结果；数据规模继续扩大时可将词法层替换为 FTS5 或 Elasticsearch，而不改变知识片段与证据模型：

- 全文检索保证技能名、企业名和原文短语的精确召回；
- 向量检索召回语义相近的岗位职责和行业场景；
- 元数据过滤限制岗位族、时间、地区、来源和审核状态；
- RAG 输出只引用检索命中的知识片段，并返回记录编号、来源 URL 和证据文本。

未配置 Embedding 时系统明确返回 `lexical` 检索模式，不伪装为向量检索。

## 5. 数据分层与状态

### 5.1 原始层

`ImportBatch` 保存文件名、文件 SHA-256、文件大小、开始/结束时间、总体状态和统计摘要。

`RawJobRecord` 保存批次、行号、原始文本、解析后的 JSON、原始行哈希、处理状态和错误信息。任何非空输入行均必须落入该层。

### 5.2 治理层

`JobPosting` 保存当前有效投影；`JobPostingRevision` 保存同一 `record_id` 的历史修订。治理状态包括：

- `valid`：结构和质量满足聚合条件；
- `review`：结构有效但存在可疑字段或低置信抽取；
- `duplicate`：精确或近似重复，保留来源但不重复计入统计；
- `quarantined`：无法解析或违反硬性字段约束；
- `superseded`：已被同一来源记录的新修订替代。

### 5.3 发布层

`JobProfileVersion`、画像关系和 `EvolutionEvent` 构成发布层。图谱接口支持：

- `draft`：包含自动生成且待审核的最新画像，供团队治理和比赛演示；
- `published`：只包含人工批准的画像和关系，供正式应用。

默认团队页面显示 `draft` 并明确审核状态，避免因单一来源导致首批图谱为空。

## 6. 实体与关系模型

### 6.1 核心实体

- `JobFamily`：岗位族及规范名称。
- `JobProfileVersion`：岗位族在一个数据截止时间形成的画像版本。
- `JobPosting`：清洗后的招聘记录。
- `JobPostingRevision`：招聘记录的历史修订。
- `Skill`：技能规范名称、类别和别名。
- `Responsibility`：归一化岗位职责。
- `IndustryScenario`：典型行业应用场景。
- `Company`：招聘企业。
- `Region`：规范化地区。
- `Source`：招聘平台、企业官网、标准或政策来源。
- `EvidenceSnippet`：原文证据、字符位置、文本哈希和来源记录。
- `KnowledgeChunk`：可检索知识片段及元数据。
- `EvolutionEvent`：两个画像版本之间的新增、删除或修改事件。
- `QualityIssue`：记录级或字段级质量问题及审核状态。

### 6.2 图谱关系

```text
(JobPosting)-[:BELONGS_TO]->(JobFamily)
(JobFamily)-[:HAS_VERSION]->(JobProfileVersion)
(JobProfileVersion)-[:REQUIRES_SKILL]->(Skill)
(JobProfileVersion)-[:PREFERS_SKILL]->(Skill)
(JobProfileVersion)-[:HAS_RESPONSIBILITY]->(Responsibility)
(JobProfileVersion)-[:APPLIES_TO]->(IndustryScenario)
(JobPosting)-[:POSTED_BY]->(Company)
(JobPosting)-[:LOCATED_IN]->(Region)
(JobPosting)-[:FROM_SOURCE]->(Source)
(Skill|Responsibility|IndustryScenario)-[:SUPPORTED_BY]->(EvidenceSnippet)
(EvidenceSnippet)-[:EXTRACTED_FROM]->(JobPosting)
(JobProfileVersion)-[:EVOLVES_FROM]->(JobProfileVersion)
```

技能、职责和场景关系至少保存：`confidence`、`evidence_count`、`prevalence`、`first_seen_at`、`last_seen_at` 和 `review_status`。版本关系保存版本差异摘要和数据截止时间。

## 7. 导入与增量更新流程

### 7.1 格式识别

解析器先识别 CSV，再对 JSON 类文件检查内容：

- `.csv` 使用表头解析；
- 首个非空字符为 `[` 时按 JSON 数组解析；
- 可完整解析为单个对象时按 JSON 对象解析；
- 否则逐行尝试 JSONL；
- 不属于上述格式时返回明确的格式错误。

JSONL 中单行失败不得导致整个文件失败。失败行写入 `RawJobRecord` 并标记 `quarantined`。

### 7.2 幂等与修订

- 文件哈希与已完成批次一致时，返回已有批次结果，不创建重复批次。
- `record_id` 和规范化内容哈希均一致时，记录为 `unchanged`。
- `record_id` 一致但内容变化时，旧投影写入修订历史，新内容成为当前投影。
- 不同 `record_id` 的内容哈希一致时，后者标记为精确重复。
- 其他同岗位族记录使用 SimHash 检测近似重复；重复记录保留，但不计入画像频率。

### 7.3 质量规则

硬性隔离条件：

- 非法 JSON 或非对象数据；
- `record_id`、岗位族、标题、来源、URL 或 JD 原文缺失；
- JD 原文不足 10 个字符且无法从其他字段恢复；
- 字段类型无法规范化。

待审核条件：

- 行业字段疑似薪资、学历或完整句子；
- 发布时间晚于采集时间，或早于采集时间 10 年以上；
- 未抽取到技能和职责；
- 来源 URL 不可识别或来源名称与 URL 域名冲突；
- 综合质量分低于 0.70；
- 大模型结果无法在原文中定位证据。

待审核记录保留在治理层；是否参与草稿画像由质量权重决定，但不得进入 `published` 图谱。

### 7.4 抽取与证据

规则抽取负责标准技能、基础职责句和显式行业词。大模型只补充规则未覆盖的职责、技能和场景。每个抽取项必须包含：

- 规范化名称；
- 类型和必备/加分属性；
- 置信度；
- 原文证据；
- 原文字符位置或可复核文本哈希。

无法提供证据的生成结果只进入审核队列，不写入正式画像关系。

### 7.5 局部画像更新

每个成功批次收集受影响的 `job_family_id`，仅重算这些岗位族。画像生成后，对规范化的技能、职责、场景、时间窗口和支持证据计算内容签名：

- 签名不变：更新批次统计，不创建新版本；
- 签名变化：关闭旧版本有效期，创建新版本和 `EVOLVES_FROM` 关系；
- 对技能、职责和场景生成 `added`、`removed`、`changed` 演化事件；
- 新版本保留参与聚合的数据截止时间和来源数量。

## 8. 知识库更新规则

每条有效 JD、证据记录和画像摘要生成稳定 `chunk_id`。知识片段包含正文、来源类型、记录编号、岗位族、发布时间、来源 URL、质量分和审核状态。

增量更新规则：

- 新记录创建新片段并进入词法检索集合；
- 修订记录使旧片段失效并创建新片段；
- 重复记录不重复索引正文，但将新增来源合并为证据元数据；
- 审核驳回的片段从默认检索范围移除；
- 配置向量索引时只计算新增或变化片段的向量；
- 可从关系型主库执行全量索引重建以恢复损坏索引。

## 9. 接口与命令

### 9.1 API

- `POST /api/data/import`：上传数据并返回批次、统计和受影响岗位族。
- `GET /api/data/import-batches`：查询导入批次和处理状态。
- `GET /api/data/quarantine`：查询异常和待审核原始行。
- `GET /api/knowledge/search`：全文/向量混合检索，返回证据与检索模式。
- `GET /api/graph`：按技术栈、级别、节点类型、岗位族、版本和发布范围获取图谱。
- `GET /api/graph/versions/{family_code}`：查询画像版本链和演化事件。
- `POST /api/graph/sync`：把主库图谱幂等同步到 Neo4j。

### 9.2 首批构建命令

项目提供可重复执行的命令，从根目录读取 `jd_raw.json`，初始化数据库、导入数据、重算画像、更新检索索引并导出图谱：

```powershell
python -m src.build_knowledge_base ..\jd_raw.json
```

生成物：

- `data/job_competency.db`：关系型知识库；
- `data/imports/<batch-id>-report.json`：导入质量报告；
- `data/exports/knowledge-graph.json`：不依赖 Neo4j 的图谱快照。

## 10. 前端范围

现有单页应用保留导航结构，并增强两个页面：

- 数据治理：显示批次、原始行、有效记录、重复、隔离、待审核和受影响岗位族；支持查看错误原因和证据。
- 全景图谱：区分岗位族、版本、技能、职责、场景和证据节点；支持按岗位族、版本、节点类型和审核状态筛选；点击节点显示来源和版本信息。

图谱节点数量过大时，接口默认返回最新画像和高频关系。用户选择岗位族或版本后再加载职责、场景和证据明细，避免一次渲染全部 JD 节点。

## 11. 失败与恢复策略

- 单行解析或校验失败：使用记录级事务保存错误，不中断后续行。
- 批次进程中断：批次标记 `failed`，已提交原始行可按批次继续处理。
- 图谱同步失败：主库提交不回滚，记录待同步状态和错误信息。
- 向量服务失败：降级为全文检索，并在响应中返回实际检索模式。
- 画像重算失败：保留旧版本为当前版本，新版本不发布。
- 导出失败：数据库状态不受影响，导出任务可重新执行。

## 12. 测试与验收

自动测试必须覆盖：

- `.json` 扩展名下 JSONL 内容的自动识别；
- 单个坏行被隔离且不影响其他行；
- 相同文件、相同记录和修订记录的幂等行为；
- 精确重复和 SimHash 近似重复；
- 质量问题分类和发布范围控制；
- 技能、职责、场景到原文证据的追溯；
- 无变化批次不生成画像版本；
- 有变化批次生成版本链和演化事件；
- 全文检索、向量降级和元数据过滤；
- Neo4j 数据映射和同步失败降级；
- 图谱节点、边、版本和筛选接口；
- 首批构建命令生成数据库、报告和图谱 JSON。

验收条件：

- 当前文件的 1855 个非空行均有原始层处理记录；
- 1 个已知非法 JSON 行进入隔离区，其余行继续处理；
- 重复执行首批构建命令不增加有效记录、知识片段或画像版本；
- 每个正式技能、职责、场景和演化事件至少关联一条证据；
- 新增一批数据时只重算涉及的岗位族；
- Neo4j 未启动时图谱 API 和 JSON 导出仍然可用；
- 全量自动测试通过，核心源码覆盖率不低于 60%；
- 导入报告明确给出原始行、解析成功、有效、待审核、重复、隔离和岗位族数量。

JD 解析准确率不从未标注的 1855 行数据中推断。比赛要求的 90% 指标继续通过独立人工标注评测集验证。

## 13. 非目标

本阶段不自动修复无法可靠判断的业务字段，不把单一来源统计包装成跨来源结论，不用无证据的大模型文本替换原始数据，也不把 Neo4j 作为唯一数据副本。新增招聘平台的数据采集本身不在本阶段范围内，但导入接口和数据模型必须兼容后续多来源批次。
