# 多源岗位采集与数据质量优化设计

**日期：** 2026-08-05  
**范围：** 公开岗位采集、来源合规、旧数据修复、跨源验证、可信时间演化、验收统计

## 1. 背景与现状

当前数据库包含1852条岗位记录，但全部来自智联招聘同一域名和同一来源类型。其中603条状态为有效，639条待复核，610条被判为重复；质量门禁中651条有效、693条待复核、503条重复、5条隔离。936条记录存在可疑发布时间，部分行业字段被薪资、学历或职位描述污染。现有数据只覆盖8个岗位族，不能充分支撑多源交叉验证、22个岗位族全景图谱和可信动态演化。

赛项最低要求是提供不少于100条岗位JD及测试用例，并验证JD解析、简历提取和匹配准确率。项目保留5000-10000条作为内部冲奖目标，但该目标必须按可用唯一岗位统计，不能使用重复、隔离或明显污染的数据凑数。

## 2. 目标与边界

本阶段建立可持续、可追溯、默认安全的岗位数据供应链，并运行首批真实岗位补采。系统应同时修复旧数据的日期与字段污染，防止新增数据继续放大现有偏差。

最终内部目标：

- 5000-7000条通过质量门禁的真实唯一岗位。
- 覆盖系统已定义的22个岗位族，每个岗位族至少100条可用样本。
- 至少3类来源，至少8个独立来源域名，单一域名占比不超过35%。
- 可信发布时间或首次观测时间覆盖率不低于90%。
- 每个进入高置信岗位画像的核心技能至少得到2类来源或3个独立域名支持。
- 原始数据、暂存数据、隔离数据、正式数据和独立评测数据严格分离。

首批实施目标为新增800-1200条通过门禁的真实唯一岗位。若公开来源的访问规则、可用性或页面结构限制导致首批不足，应如实报告已获得数量，不得生成虚构岗位补足目标。

本项目不采集求职者简历、联系方式或其他个人信息；只处理公开发布的岗位说明和必要的企业、地区、时间、来源字段。

## 3. 方案选择

采用“合规白名单 + 暂存采集 + 质量门禁 + 人工复核 + 增量导入”的混合方案。

不采用无边界批量爬取。企业招聘网站只有在公开访问且站点规则允许时才能启用自动采集；需要登录、验证码、签名绕过、浏览器指纹伪装或未经授权接口的来源一律禁用。服务条款不清晰的企业站只允许人工整理公开详情URL或导出内容，不启用自动翻页抓取。

不使用来源不明的网络数据集直接补量。开放数据集只有在能保留原始来源URL、发布时间、许可说明和稳定记录编号时才能进入暂存区。

## 4. 来源白名单与合规门禁

新增来源注册表，每个来源包含：

- `source_id`：稳定来源编码。
- `source_name`：展示名称。
- `source_type`：`public_service`、`university_recruitment`、`company_official`或`authorized_platform`。
- `base_url`与允许访问的路径范围。
- `collection_mode`：`public_html`、`public_json`、`manual_url_manifest`或`file_import`。
- `compliance_status`：`approved`、`manual_only`、`blocked`或`pending_review`。
- `compliance_note`：访问规则、条款或人工确认记录。
- `rate_limit_seconds`、单批最大页数和单批最大记录数。
- 解析器名称、解析器版本和启用状态。

首批候选来源类型：

1. 政府公共招聘服务，如中国公共招聘网公开岗位页面。
2. 高校就业服务，如国家大学生就业服务平台及高校审核发布的公开招聘信息。
3. 企业官方招聘，采用人工URL清单或经确认允许的公开页面。

任何来源只有在 `compliance_status=approved` 时允许自动请求；`manual_only` 只接受团队成员提供的公开URL或页面导出文件；`blocked` 和 `pending_review` 不执行采集。

## 5. 采集架构

```text
来源注册表
  -> 合规检查
  -> 限速请求与缓存
  -> 列表页/详情页解析
  -> 原始页面快照与来源元数据
  -> 统一岗位记录
  -> 暂存质量门禁
  -> 批次报告与人工复核
  -> 数据库备份
  -> 增量导入
  -> 质量管线、岗位画像、知识库与图谱增量更新
```

采集命令默认使用 `--dry-run`，只生成暂存数据和报告。正式导入需要显式使用 `--commit`，并在导入前备份SQLite数据库。采集中断后可从批次检查点继续，不重复请求已缓存的详情页。

网络请求遵循来源级速率限制，使用明确标识研究用途的User-Agent，设置超时、有限重试和指数退避。收到401、403、429、验证码页、登录页或结构异常时立即停止该来源，不尝试绕过限制。

## 6. 统一岗位记录

每条暂存记录必须包含：

- `record_id`、`collector_id`和`job_family_id`。
- 原始岗位名称、企业名称、行业、地区。
- `source_id`、`source_name`、`source_type`、`source_domain`和`source_url`。
- 来源岗位编号 `source_record_id`。
- `published_at`、`published_at_evidence`和`published_at_confidence`。
- `collected_at`、`first_seen_at`和`last_seen_at`。
- 经验、学历、薪资和岗位说明原文。
- `snapshot_hash`、`parser_name`、`parser_version`和`collection_method`。
- 合规说明、页面标题、响应状态和批次编号。

来源未明确展示发布时间时，`published_at`保持为空，不从岗位描述中的教育时间、项目时间或任职时间推断。`collected_at`作为本次观测时间，`first_seen_at`用于后续观测演化，但两者不得伪装成发布时间。

## 7. 岗位族识别与配额

复用系统现有22个岗位族：Java、Python后端、Go、前端、DevOps、SRE、云原生、AI智能体、大模型应用、RAG、MLOps、多模态、提示词工程、AI解决方案、大数据开发、数据治理、数据工程、物联网、边缘计算、网络安全、数字孪生和机器人智能系统。

分类采用“岗位标题规则 + 职责技能证据 + 可选大模型复核”。规则分类先执行；大模型只对低置信或多标签冲突案例给出候选，不直接写入正式岗位族。每个分类结果保存命中标题、技能和职责证据。

采集调度优先补齐当前缺失的14个岗位族。单一岗位族达到目标配额后降低采集优先级，防止大数据岗位继续挤占其他领域。

## 8. 旧数据修复

旧数据修复在数据库副本上先执行并生成差异报告，确认后再应用到主库：

1. 重新解析根目录 `jd_raw.json`，无法解析的记录保留到隔离文件，不静默丢弃。
2. 对936条可疑发布时间逐条判断是否有来源字段证据；没有证据的设置为空并标记 `published_date_untrusted`。
3. 行业字段匹配薪资、学历、岗位要求或长句模式时改为 `unknown`，保留原值和修复原因。
4. 重新计算内容哈希、SimHash、精确重复和近似重复关系。
5. 重新运行岗位层级识别和数据质量门禁。
6. 不删除原始记录；修复前值、修复后值、规则版本和时间写入修订记录或审计报告。

修复后的历史记录只有在 `gate_status=valid`、非重复且日期可信时才进入季度演化。日期为空的有效岗位仍可参与总体岗位画像，但不得参与时间趋势计算。

## 9. 跨来源验证与图谱置信度

岗位画像和技能边不再只依据样本总量。每个技能同时统计：

- 支持岗位数与岗位占比。
- 独立来源类型数。
- 独立来源域名数。
- 企业数量。
- 时间覆盖范围。
- 必备或加分要求比例。
- 来源质量加权置信度。

核心技能进入高置信画像需要满足最低样本量，并至少获得2类来源或3个独立域名支持。只有单一来源支持的技能可以保留，但标记为“单源证据”，不得自动升级为高置信核心技能。

新岗位发现需要同时满足样本增长、来源多样性、技能组合新颖性和持续观测条件。仅由一个来源集中发布、重复转载或标题营销产生的岗位不得自动判定为新兴岗位。

## 10. 可信动态演化

时间演化使用两类时间轴并明确区分：

- `published_at`：来源页面明确展示的发布时间，适合季度岗位需求分析。
- `first_seen_at`：系统首次观测时间，适合持续采集后的增量变化分析。

系统不混合这两类时间生成同一趋势。演化事件必须展示时间口径、样本数、来源数和证据链接。历史可疑日期修复为空后，相关伪趋势和伪季度画像需要重新构建并废弃旧派生结果。

## 11. 数据质量门禁

新增或强化以下门禁：

- 来源必须在白名单中，URL协议与域名匹配注册表。
- 岗位说明有效文本长度不少于40个规范字符。
- 来源编号、URL和快照哈希用于幂等去重。
- 发布时间晚于采集时间、远早于采集时间或缺乏页面证据时降级或复核。
- 行业、地区、学历、经验和薪资执行字段类型与串列检测。
- 标题与岗位说明缺少能力证据时进入复核。
- 同公司、同标题、同地区和高文本相似度记录识别为近似重复。
- 页面为登录、验证码、错误或空内容时整条隔离。

每个批次输出原始数、解析数、有效数、复核数、隔离数、重复数、来源分布、岗位族分布、日期可信率、字段缺失率和错误明细。

## 12. 验收统计优化

界面和验收服务同时保留“原始岗位数”和“可用唯一岗位数”，但内部5000-7000目标按后者判断。新增指标：

- 可用唯一岗位数。
- 有效率、重复率、待复核率和隔离率。
- 来源类型数、来源域名数和最大单域名占比。
- 岗位族覆盖数及每族最低样本量。
- 可信日期覆盖率。
- 跨来源核心技能覆盖率。
- 可用于季度演化的岗位数。

现有 `raw_job_postings` 指标继续展示原始规模，但不能单独触发内部数据就绪状态。

## 13. 文件、服务与界面

新增独立采集模块，避免把网络访问混入现有导入服务：

- 来源注册与合规检查。
- HTTP请求、缓存和限速。
- 来源适配器与统一字段映射。
- 批次暂存、检查点和质量报告。
- 旧数据修复命令。
- 采集验收统计服务。

界面只新增面向业务人员的数据健康信息：可用岗位量、来源结构、岗位覆盖、日期可信度和最近批次结果。具体比赛编号、奖项目标和规则原文仍不出现在系统界面。

## 14. 错误处理与安全

- 来源未批准：拒绝自动采集并说明状态。
- 401、403、429、验证码或登录页：停止来源，不重试绕过。
- 页面结构变化：隔离该批记录并标记解析器版本。
- 批次未达到质量门禁：只保留暂存与报告，不导入数据库。
- 正式导入失败：事务回滚并保留数据库备份。
- 图谱重建失败：岗位数据保留，派生状态标记失败，允许重试。
- 所有递归清理只作用于项目内已验证的采集暂存目录。

## 15. 测试方案

采用测试驱动实现，覆盖：

- 来源白名单、合规状态和域名约束。
- 限速、缓存、重试上限以及401、403、429停止逻辑。
- HTML、JSON和人工URL清单解析。
- 字段规范化、日期证据和串列检测。
- 精确去重、近似去重和跨批次幂等。
- 岗位族分类与低置信复核。
- 旧数据修复差异报告和数据库备份。
- 跨来源技能置信度和单源降级。
- 可信发布时间与首次观测时间分离。
- 验收统计按可用唯一岗位计数。
- 现有导入、知识库、图谱、演化、匹配和界面测试继续通过。

网络测试使用本地固定响应样本，不依赖实时网站。真实来源连通性使用单独的低频冒烟检查，失败不得影响离线单元测试。

## 16. 实施与验收顺序

1. 实现来源注册、采集批次、统一记录和离线测试。
2. 实现旧数据审计与修复报告，不立即修改主库。
3. 实现跨来源统计、可信时间口径和新验收指标。
4. 对批准来源执行小规模冒烟采集，每来源不超过20条。
5. 审查质量与合规结果后扩大首批采集至800-1200条有效唯一岗位。
6. 备份数据库并增量导入，通过现有硬指标管线重建知识库、画像和图谱。
7. 验证新旧岗位案例、动态演化、来源证据和完整测试。

完成标准：采集管线可重复运行；旧数据修复可审计；正式库不包含虚构补量数据；首批新增岗位具有真实来源和完整采集时间；验收统计使用可用唯一岗位；完整自动化测试通过且覆盖率不低于现有门槛。
