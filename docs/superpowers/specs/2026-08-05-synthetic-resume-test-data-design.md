# 合成简历测试数据设计

**日期：** 2026-08-05  
**范围：** 64份合成简历、标准答案、自动评测数据与可持续生成工具

## 1. 目标与边界

为现有简历解析、人岗匹配、岗位推荐和学习路径功能补充可重复运行的测试数据。数据覆盖当前数据库中的8个主要岗位族，用于功能回归、边界验证和演示验收。

所有生成记录必须显式标注 `synthetic=true` 和 `data_usage=test_only`。合成简历不得计入真实岗位采集量，不得混入真实简历库，不得作为比赛中真实数据规模或模型准确率的证明。正式准确率仍使用独立人工标注的数据集测量。

## 2. 方案选择

采用确定性模板生成方案：由岗位族配置、案例矩阵和固定随机种子生成简历文本、结构化标准答案及评测记录。该方案便于复现、审查和持续扩充。

本阶段不使用大模型自由生成主体数据。大模型生成虽有语言多样性，但标签容易与文本漂移，不利于稳定回归。后续可以在人工复核后增加少量语言扰动样本，并继续保留明确的合成标记。

## 3. 数据规模与分布

共生成64份简历，覆盖以下8个岗位族：

| 岗位族编码 | 岗位名称 | 数量 |
| --- | --- | ---: |
| `BIG_DATA_DEVELOPER` | 大数据开发工程师 | 8 |
| `DATA_ENGINEER` | 数据工程师 | 8 |
| `DATA_GOVERNANCE_ENGINEER` | 数据治理工程师 | 8 |
| `EDGE_COMPUTING_ENGINEER` | 边缘计算工程师 | 8 |
| `DIGITAL_TWIN_ENGINEER` | 数字孪生工程师 | 8 |
| `CYBERSECURITY_ENGINEER` | 网络安全工程师 | 8 |
| `ROBOTICS_ENGINEER` | 机器人与智能系统工程师 | 8 |
| `IOT_ENGINEER` | 物联网工程师 | 8 |

每个岗位族使用同一组8案例矩阵：

| 序号 | 人才层级 | 预期匹配档位 |
| ---: | --- | --- |
| 1 | junior | high |
| 2 | mid | high |
| 3 | senior | high |
| 4 | junior | medium |
| 5 | mid | medium |
| 6 | senior | medium |
| 7 | junior | low |
| 8 | mid | low |

总体分布为：high 24份、medium 24份、low 16份；junior 24份、mid 24份、senior 16份。

## 4. 简历内容设计

每份简历包含职业概述、专业技能、工作经历、项目经历、教育经历和证书资质中的适用章节。个人姓名、电话、邮箱、公司名称和学校名称均使用明显的虚构占位内容，不引用真实个人身份。

文本覆盖以下解析场景：

- 中文标准章节、Markdown标题和紧凑叙述三种版式。
- `YYYY.MM-YYYY.MM`、`YYYY-MM 至 YYYY-MM`、中文年月和“至今”等日期表达。
- 单段经历、多段连续经历和少量时间重叠经历。
- 技能清单、工作证据和项目证据中的技能表达。
- “正在学习”“未使用”“计划学习”等否定或弱意图表达，验证系统不会错误计入已掌握技能。
- 百分比、时延、吞吐量和人日等量化成果。
- 核心技能、相邻技能、缺失技能和跨岗位干扰技能。

技能名称必须来自 `src/skill_ontology.py` 的规范技能目录。每个岗位族配置核心技能、辅助技能和干扰技能，high、medium、low通过技能覆盖、经验年限、项目证据和技能时效共同形成，不只依赖文本中出现的技能数量。

## 5. 文件与字段

生成内容放在 `data/synthetic_resumes/`：

- `resumes/SYN-CV-0001.txt` 至 `resumes/SYN-CV-0064.txt`：独立简历正文。
- `manifest.jsonl`：每份简历的元数据和标准答案。
- `benchmark-resume-extraction.jsonl`：64条简历解析评测记录。
- `benchmark-matching.jsonl`：64条人岗匹配评测记录。
- `benchmark-recommendation.jsonl`：64条岗位推荐评测记录。
- `README.md`：数据用途、生成命令、字段说明和限制。

`manifest.jsonl` 每行至少包含：

```json
{
  "resume_id": "SYN-CV-0001",
  "synthetic": true,
  "data_usage": "test_only",
  "target_family": "DATA_ENGINEER",
  "target_level": "junior",
  "expected_band": "high",
  "resume_path": "resumes/SYN-CV-0001.txt",
  "expected": {
    "skills": ["Python", "ETL", "MySQL"],
    "experience_years": 2.0,
    "education": ["本科"],
    "work_ranges": [{"start": "2023-07", "end": "2025-06"}],
    "project_skills": ["Python", "ETL"],
    "evidence_substrings": ["使用Python和ETL建设数据处理任务"]
  }
}
```

所有JSONL文件使用UTF-8编码，一行一个完整JSON对象；标识符必须唯一且稳定。重新运行生成工具时，同一版本和随机种子应得到字节级一致的输出。

## 6. 生成组件与数据流

新增独立生成模块，职责如下：

1. 岗位族配置定义规范技能、辅助技能、干扰技能、项目场景和岗位名称。
2. 案例矩阵定义层级、匹配档位、经验、版式、日期样式和边界场景。
3. 简历渲染器根据配置生成正文，同时返回结构化标准答案。
4. 评测构建器将标准答案转换为现有评测服务支持的 `resume_extraction`、`matching` 和 `job_recommendation` 记录。
5. 校验器在写入前检查数量、分布、技能合法性、路径、编号和JSONL格式。

生成器只读取代码中的静态岗位配置和技能本体，不读取或修改生产数据库。这样可以避免当前岗位画像更新导致历史测试样本悄然变化。

## 7. 评测接入

简历解析集直接使用生成文本及标准答案，测量技能、经验、学历、时间线、项目技能、量化成果、证据有效性和解析方式。

人岗匹配集为每份简历提供稳定的结构化候选人档案和目标岗位画像，并标注 high、medium、low。预期档位由预先定义的案例矩阵决定；生成后必须通过当前匹配引擎执行一次校准检查。若实际档位与预期不一致，应调整测试配置或暴露算法问题，不得在运行后直接篡改标签迎合结果。

岗位推荐集为每份简历提供至少5个不同岗位族候选，并为目标岗位族和合理的相邻岗位族提供相关性等级。评测继续使用Top-1 Accuracy、Recall@5、MRR和NDCG@5。

学习路径不新增独立准确率标签，但每个high、medium、low案例均运行路径生成，并验证阶段顺序、技能缺口、前置关系、预计提分上限和非虚构表述。

## 8. 质量门禁与错误处理

生成完成必须满足：

- 简历文件恰好64份，8个岗位族各8份。
- high、medium、low分别为24、24、16份。
- junior、mid、senior分别为24、24、16份。
- 所有技能均可由技能本体规范化，预期技能没有重复项。
- 每个 `evidence_substrings` 都能在对应简历正文中找到。
- 时间范围合法，合并后的经验年限与标准答案一致。
- 每个评测文件可逐行解析，`case_id` 和 `resume_id` 全局唯一。
- 不含真实联系方式、真实来源链接或未标注的合成记录。

任一校验失败时，生成命令返回失败状态并报告具体编号和字段，不留下部分生成结果。输出先写入临时目录，全部通过后再替换目标目录。

## 9. 自动化测试

先增加失败测试，再实现生成器。测试覆盖：

- 固定种子的确定性输出。
- 64份规模及岗位族、层级、匹配档位分布。
- 简历正文与manifest标准答案一致。
- JSONL字段满足现有评测服务输入格式。
- 否定技能不被规则解析器计入。
- 时间线、项目技能、成果和证据片段可被解析。
- 三类评测文件可被评测服务完整执行。
- 现有完整测试套件继续通过，覆盖率不低于项目当前门槛。

## 10. 验收标准

- 运行一次命令即可重新生成全部64份简历及三类评测数据。
- 生成结果不依赖DeepSeek或网络服务。
- 数据目录和每条记录均明确标注合成测试用途。
- 简历覆盖8个现有岗位族、3个人才层级和3个匹配档位。
- 系统能够批量解析这些简历，并执行匹配、推荐和学习路径验证。
- 自动校验与完整测试全部通过。
- 文档明确区分合成测试数据和比赛真实采集、人工标注数据。
